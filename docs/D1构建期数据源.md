## 1. 为什么是构建期

### 1.1 架构红线

站点必须保持**纯静态**：SQLite 只用于本地内容管理与构建，**不得加入运行时数据库或上传接口**
（见仓库根目录 `新会话必读.md`）。因此 D1 不可能在浏览器里被访问，也不能在 `functions/` 里
提供内容接口；它只能作为「另一种构建期内容源」出现。

### 1.2 D1 binding 在构建期不可见

Cloudflare 的 **D1 binding 只对 Pages Functions / Worker 运行时可见**（即 `context.env.DB`），
`astro build` 是在构建容器里跑的普通 Node 进程，**拿不到 binding**。
官方说明：<https://developers.cloudflare.com/pages/functions/bindings/index.md>

所以构建期取 D1 数据只有两条路：

| 方式 | 本仓库对应 | 说明 |
|---|---|---|
| D1 REST 查询接口（推荐） | `createContentSource()` 的 `CONTENT_SOURCE=d1` 分支；`pnpm d1:export` | 用 `fetch` 直接 POST 查询接口，凭据走环境变量；导出脚本也是逐表查询后本地渲染快照 |
| 官方 Export API / `wrangler d1 export` | `d1-client.mjs` 里的 `exportSql()`（当前没有脚本调用） | 导出整库 SQL 再本地重放；`wrangler` 未加入依赖，`exportSql()` 也未经真实 D1 验证 |

现有实现选择 REST 查询：`scripts/content-sync.mjs` 在生成 `src/data/content.json` 之前调用
`createContentSource()`；`CONTENT_SOURCE=d1` 时数据来自 D1 REST，否则仍读 `data/content.db`。
生成完 JSON 后前端代码只读静态 JSON，运行时与 D1 无关。

> 构建期在 Pages 上也能读到环境变量（Pages 的构建环境变量对构建与运行时都可用），
> 所以「Pages 构建时用 D1 REST」在平台上是可行的；真实 D1 上的建表 / 视图 / 推送 / 导出 / 构建
> 已于 2026-10-24 端到端验证通过，剩余待确认项见第 8.2 节。

## 2. 工作流

### 2.1 日常本地（默认，离线可用）

```bash
# 1) 用现有工具改本地内容库（管理工具 / pnpm content:add 等）
# 2) 生成 src/data/content.json 与 data/content-dump.sql
pnpm content:sync
# 3) 构建（build 脚本会在 astro build 前自动再跑一次 content-sync）
pnpm build
```

不设 `CONTENT_SOURCE` 时行为与改造前完全一致，**不需要任何 Cloudflare 凭据，也不需要网络**。
`content.json` 内容未变化时不会改写文件。

### 2.2 本地内容 → Cloudflare D1 → 构建

```bash
# 1) 先确认本地内容能正常生成（离线）
pnpm content:sync

# 2) 检查推送计划（默认 dry-run：不联网、不写 D1）
pnpm d1:push

# 3) 真正写入 D1（幂等：先清空公开表，再按外键顺序插入；首次可加 --schema 建表）
pnpm d1:push --yes
# 首次或远端还没有表时：
pnpm d1:push --schema --yes

# 4) 构建期从 D1 取数
CONTENT_SOURCE=d1 pnpm build
```

PowerShell 里设置环境变量：

```powershell
$env:CONTENT_SOURCE = "d1"
$env:CLOUDFLARE_ACCOUNT_ID = "<账号 ID>"
$env:CLOUDFLARE_D1_DATABASE_ID = "<D1 数据库 UUID>"
$env:CLOUDFLARE_API_TOKEN = "<API Token，读取需要 D1 Read>"
pnpm build
```

Windows cmd 没有内联环境变量语法；跨 shell 可以用仓库已有的 devDependency：

```bash
npx cross-env CONTENT_SOURCE=d1 pnpm build
```

> ⚠️ 用 `CONTENT_SOURCE=d1` 构建会重写 `src/data/content.json` 与 `data/content-dump.sql`，
> 内容是**来自 D1 的那一份**。构建完请用 `git diff` 确认这是你想要的，不要把云端快照误当成本地内容提交。
> 想回到本地内容：不设 `CONTENT_SOURCE`（或设为 `local`）再跑一次 `pnpm content:sync`。

### 2.3 D1 → 本地 SQL 快照

```bash
# 默认 dry-run：联网读取并报告行数，但不落盘
pnpm d1:export

# 写入 data/d1-export.sql（内容没变化时不会改动文件）
pnpm d1:export --write

# 自定义文件名（相对 data/，必须是 .sql）
pnpm d1:export --write 备份/d1-2026-10-24.sql
```

快照格式与 `data/content-dump.sql` 一致，可以用 sqlite3 重放；**重放前务必读第 10 节**：
快照会先清空四张公开表，`item_audio` 还会被级联清掉。

## 3. 环境变量

所有变量都只从**进程环境**读取（仓库没有 dotenv 之类的依赖，**不会自动加载 `.env`**）。

| 变量 | 何时需要 | 默认 | 说明 |
|---|---|---|---|
| `CONTENT_SOURCE` | 构建 / `content:sync` | `local` | 只支持 `local`（读 `data/content.db`）与 `d1`（构建期 REST）。大小写与首尾空白会被规范化；其他值直接报错 |
| `CLOUDFLARE_ACCOUNT_ID` | 使用 D1 时 | 无 | Cloudflare 账号 ID（Account tag） |
| `CLOUDFLARE_D1_DATABASE_ID` | 使用 D1 时 | 无 | D1 数据库 UUID（面板里的 Database ID，不是数据库名） |
| `CLOUDFLARE_API_TOKEN` | 使用 D1 时 | 无 | API Token。构建/导出只需要 **D1 Read**；`d1:push --yes` 需要 **D1 Edit** |
| `CLOUDFLARE_D1_API_BASE` | 可选 | `https://api.cloudflare.com/client/v4` | 覆盖 API 根地址（自建代理、mock 测试）。末尾多余斜杠会被去掉 |
| `D1_TIMEOUT_MS` | 可选 | `30000` | 单次 HTTP 请求超时（毫秒）。同时覆盖「等响应头」和「读响应体」；非正数/非法值回落到默认值 |

补充：

- 只跑 `pnpm d1:push`（dry-run）**不需要凭据**：它只在输出里提示缺少哪些变量，不校验、不联网。
  但 `pnpm d1:export` 的 dry-run 仍然要联网读 D1，所以**必须**有凭据。
- `CONTENT_SOURCE=d1` 时 `content-sync` / `build` 需要三个凭据变量齐全，缺一个都会在发请求前抛
  `D1ConfigError`，并在错误信息里列出缺的变量名与赋值示例。
- 建议给「构建/导出」与「推送」分别建 Token，构建用的 Token 只给 D1 Read，泄露时损失最小。
- 在 Cloudflare Pages 上，把上面变量加到项目的构建环境变量（Production 与 Preview 都加），
  构建命令保持 `pnpm build` 即可；不要把 Token 写进仓库文件。

## 4. 安全

实现里已经做了这些约束（改代码时不要破坏）：

1. **Token 只从环境变量读取**：`createD1ClientFromEnv()` 是唯一入口；不写盘、不写进任何生成物。
2. **Token 不拼进 SQL**：SQL 与绑定参数（`params`）里都不会出现 Token；Token 只进 `Authorization` 头。
3. **Token 不打印**：日志/错误信息统一经过 `scrubSecret()`，命中时替换成 `[REDACTED]`；
   `describe()` 只显示打码后的数据库 ID（`****` 或 `abcd…wxyz`），不显示 Token。
4. **错误对象也打码**：`D1ApiError.errors` 在构造时递归处理，字符串值全部过 `scrubSecret`，
   结构和非字符串字段（如 `code`）保留。调用方直接 `console.log(error.errors)` 或
   `JSON.stringify(error.errors)` 也不会泄露 D1 回显的 Token。
   `normalizeResult` 的「第 N 条语句未成功」同时带出已打码的子错误。
5. **一次性下载地址不落日志**：导出接口的 `signed_url` 视同凭据，只用于内存里的下载请求。
6. **`.env` 已被 gitignore**（`.gitignore` 的 `.env` / `.env.*` 规则，`.env.example` 例外）。
   注意 `.env.example` 是公开样例，当前只放 `PUBLIC_*` 公开读地址，**绝不要往里面写 Token**；
   而且本仓库脚本不会自动读取 `.env`，写了也不会生效。
7. **SQL 预览有长度上限**：错误信息里的 SQL 只保留前 160 个字符，避免长内容刷屏。

需要清醒认识边界：

- 环境变量本身对同机同用户的其他进程/崩溃转储是可见的；不要在不可信机器上长期导出 Token。
- `D1ApiError` 的打码发生在**客户端内部构造时**（它知道 Token）。如果自己 `new D1ApiError(message, { errors })`
  且不传 `secret`，构造函数无法知道要擦哪个字符串，原始 `errors` 不会被擦除。
- 命令日志（例如 shell 的 `set -x`、CI 的调试日志）可能把环境变量本身打印出来，这与本代码无关，
  需要从 shell/CI 侧避免。

## 5. 命令说明

两个命令都遵循「**默认 dry-run，显式开关才产生副作用**」的约定，参数解析风格与
`scripts/content-cli.mjs` 一致（`--flag` / `--key value`）。

### 5.1 `pnpm d1:push`（本地 SQLite → D1）

```text
node scripts/d1-push.mjs [--yes] [--schema] [--per-request <1-50>]
                         [--no-sequence] [--allow-empty] [--dry-run] [--help]
```

| 选项 | 作用 |
|---|---|
| 无参数 | dry-run：读本地库、拆 schema（如果给了 `--schema`）、打印完整计划；**不联网、不写 D1** |
| `--yes` | 真正写入 D1。会先清空公开表，再按父→子顺序插入；可重复执行（幂等） |
| `--schema` | 写入前先执行 `data/schema.sql`：拆成单条语句执行。会剔除 `PRAGMA` / 事务控制语句与私有表语句 |
| `--per-request <n>` | 每个 HTTP 请求带几条语句，1–50，默认 20。见第 6 节 |
| `--no-sequence` | 不读也不写 `sqlite_sequence`（D1 拒绝该表时的退路） |
| `--allow-empty` | 本地公开表全部为空时仍允许 `--yes`。默认拒绝，避免误把 D1 清空 |
| `--dry-run` | 显式 dry-run（与不加 `--yes` 等价）；不能和 `--yes` 同时用 |
| `--help` | 帮助 |

执行顺序（`--yes`）：

1. `--schema` 存在时，先执行建表语句（`CREATE TABLE IF NOT EXISTS` / `CREATE INDEX` / `CREATE VIEW`）。
2. 按外键子→父清空：`items` → `stacks` → `groups` → `settings`。
3. 清空 `sqlite_sequence` 里 `groups/stacks/items` 的行（`--no-sequence` 时跳过）。
4. 按父→子分批插入：`groups` → `stacks` → `items` → `settings`。
5. 写回 `sqlite_sequence`（`--no-sequence` 时跳过）。

需要注意：

- **`--schema` 只建表，不补列**：schema 全是 `CREATE TABLE IF NOT EXISTS`，远端旧结构缺列时不会自动
  加列，需要用 `wrangler d1 execute` 手动 `ALTER TABLE`（本仓库没有迁移器）。
- 本地公开表全空时，`--yes` 会被拒绝；确认要清空 D1 才加 `--allow-empty`。
- 中途失败**没有整体事务保证**（见第 8 节），可能留下「已清空但没写全」的 D1；修正原因后重跑即可。
  不要在中途失败后手工往 D1 补数据，容易与本地内容产生 id 冲突。
- `sqlite_sequence` 读写是尽力而为：D1 拒绝时只警告，不中断内容推送；可用 `--no-sequence` 明确跳过。
- `--per-request` 的 50 是保守上限，尚未压测；不是「建议调大」。

### 5.2 `pnpm d1:export`（D1 → 本地 SQL 快照）

```text
node scripts/d1-export.mjs [--write] [--page-size <1-1000>] [--dry-run] [文件名]
```

| 选项 / 参数 | 作用 |
|---|---|
| 无参数 | dry-run：联网从 D1 读取公开表并报告行数/页数；**不落盘** |
| `--write` | 真正写入文件（默认 `data/d1-export.sql`） |
| `--page-size <n>` | 每页行数，1–1000，默认 100。见第 6 节 |
| `--dry-run` | 显式 dry-run（与不加 `--write` 等价）；不能和 `--write` 同时用 |
| `文件名` | 可选的相对路径，相对 `data/`，必须以 `.sql` 结尾；不能是绝对路径、不能跳出 `data/`、不能覆盖 `data/schema.sql` |
| `--help` | 帮助 |

行为细节：

- 通过查询接口按 `ORDER BY <key> LIMIT n OFFSET m` 逐页拉取 `groups / stacks / items / settings`，
  再渲染成与 `exportDump()` 相同形态的 `.sql`（文件头 + DELETE 前导 + INSERT + `sqlite_sequence`）。
- 拉取 `sqlite_sequence` 是尽力而为：失败只提示并跳过序列行。
- 如果 D1 上存在管理工具私有表（`item_audio / audio_cleanup / audio_retired`），
  导出会**忽略它们并提示**，快照里没有这些数据。
- 内容是确定性的（没有时间戳），配合 `writeIfChanged()`：数据没变时完全不改动文件。
- 默认只导出公开表；`sqlite_sequence` 行也只在能读到时才写入。

重放（**先读第 10 节并备份**）：

```bash
sqlite3 data/content.db < data/d1-export.sql
```

## 6. 平台限制与分批策略

官方限制（来源见第 12 节）：

| 限制 | 数值 | 本仓库的应对 |
|---|---|---|
| 单次查询最多绑定参数 | **100 个/查询** | `d1:push` 按「每批行数 = floor(100 / 列数)」切分；客户端在发请求前预检，超过直接抛 `D1ConfigError` |
| 单条 SQL 大小 | **100 KB** | `d1-push` 用 90 KB 软上限二次切分；单行渲染就超限时直接报错，不盲目发请求 |
| 单次查询时长 | **30 秒** | `D1_TIMEOUT_MS` 默认 30000；内容库很小，单批只写几行到几十行 |
| 单行 / 字符串 / BLOB | **2 MB** | 单条 SQL 软上限通常先触发；超限时脚本报错中止 |
| `params` 类型 | 官方标注 `array of string` | 客户端把所有绑定参数统一转成字符串（数字、布尔、bigint）；NULL 不能绑定 |

### 6.1 推送时的分批

- **每批行数 = `floor(100 / 列数)`**。以当前 `data/schema.sql` 为例：
  `groups` 6 列 → 每批 16 行；`stacks` 5 列 → 20 行；`items` 18 列 → 5 行；`settings` 2 列 → 50 行。
- 一个 INSERT 语句可以包含多行；每一行的每一列要么是绑定参数 `?`，要么是内联的 `NULL`。
  **NULL 用 SQL 字面量内联**（`params` 表达不了 NULL），非 NULL 值走参数绑定。
  所以每批的实际绑定参数通常少于 100。
- 单条 INSERT 再受 90 KB 软上限约束：长路径 / 长备注导致超限时会提前收尾另起一条。
- `--per-request` 只控制「一个 HTTP 请求里塞几条语句」（默认 20，上限 50），
  不改变上面的单条 SQL / 参数限制。
- 本地内容库很小，这些上限远未逼近；数据量增大时要重新核对行数与 30 秒限制。

### 6.2 读取时的分页

- D1 的 HTTP 查询接口没有游标，`selectAll()` 用 `LIMIT/OFFSET` 逐页读，默认每页 100 行。
- `d1:export` 的 `--page-size` 默认 100；**不要盲目调大**：官方没有写明单次 REST 响应最多返回多少行，
  页越大越容易触碰未知上限。
- OFFSET 分页在两次查询之间有人写库时可能漏行/重复；构建期只读场景可接受。
  需要更强一致性时可用 `selectAllKeyset()`（键集分页），但要注意第 9 节的 `firstPageSql` 约定。

### 6.3 超时

- 客户端对每个请求使用 `AbortController`：超过 `D1_TIMEOUT_MS` 会中止请求并抛 `D1ApiError`。
- 超时覆盖「等响应头 + 读响应体」两个阶段；不会出现响应头已回、body 卡住导致无限挂起。
- 官方平台对查询还有 30 秒硬限制；即使把 `D1_TIMEOUT_MS` 调大也绕不过去。

## 7. 只推公开表

`d1:push` 的推送清单是硬编码的公开内容表：

| 表 | 推送？ | 用途 |
|---|---|---|
| `groups` | ✅ | 分组（页面卡片） |
| `stacks` | ✅ | 合集（堆叠按钮） |
| `items` | ✅ | 音频条目（普通 + 彩蛋） |
| `settings` | ✅ | 全局文案（空栏目提示等） |
| `item_audio` | ❌ | 管理工具私有音频目录，只应存在于本地 |
| `audio_cleanup` | ❌ | 管理工具私有清理队列，只应存在于本地 |
| `audio_retired` | ❌ | 管理工具私有退役记录，只应存在于本地 |

约束在代码里有两道：

1. `buildSchemaStatements()` 会剔除任何提及私有表的 schema 语句；
2. `buildPushPlan()` 开头断言公开表清单里不含私有表。

私有表**绝不推到 D1** 的原因：

- 构建期只需要展示内容，不需要管理工具的物理文件目录；
- 这些目录包含本地音频资产元数据（路径、哈希等），不应随 D1 往返；
- D1 上的数据应只包含「站点展示所需的最小集合」。

如果 D1 上被人为放入了私有表：`d1:export` 会忽略并提示；但 `content-sync` 的 D1 模式在物化
`content-dump.sql` 时会对这些 optional 表「尽力而为」，可能把它们带进快照。不要这样操作。

| 分批 INSERT | ✅ groups 8 / stacks 1 / items 8 / settings 2，D1 回报 `changes` 合计 **19** |
| `params` 全字符串化 | ✅ 真实 D1 接受字符串参数写入数值列（`special_effect`=0/1、`info_duration`=12.5 等） |
| 私有表排除 | ✅ `item_audio` / `audio_cleanup` / `audio_retired` 未建表、未推送 |
| `pnpm d1:export --write` | ✅ 真实 D1 拉取：8 / 1 / 8 / 2 行 + `sqlite_sequence` 3 行 → 19 条 INSERT 快照 |
| `CONTENT_SOURCE=d1 pnpm build` | ✅ 3 页构建成功，生成的数据与本地源**逐字节一致**（仅来源标记不同，见 8.3） |

### 8.2 仍未验证

1. **batch 是否整体事务化**：官方只说明按顺序执行；`d1:push` 按「顺序执行、失败重跑」设计，没有验证「一个 batch 中途失败会不会全部回滚」。
2. **REST 单次响应行数上限**：官方文档没有写明；分页默认取 100 行是保守值（本次数据量太小，未触及上限）。
3. **官方 Export API 的中间状态**：`exportSql()` 的宽松轮询判断未在真实 D1 上跑到完成态（本次导出走的是分页 SELECT，未触发该路径）。
4. **30 秒查询限制与 `D1_TIMEOUT_MS` 的真实交互**：客户端超时与平台超时的先后顺序未验证。
5. **快照重放到真实 `data/content.db`**：本次只生成并比对了快照内容，没有把 `d1-export.sql` 真正重放进本地库。
6. **大规模数据**：本次仅 19 行，分批上限（100 参数 / 100 KB）在真实数据量下未压测。

### 8.3 真机验证发现的两个行为（设计如此，但会影响 CI）

1. **`content.json` 的来源标记会不同**：D1 模式生成的 `_generated.note` / `_generated.source` 为「Cloudflare D1」，本地模式为「data/content.db」。**内容数据（分组 / 条目）逐字节相同**，只有这 4 行元数据不同 —— 因此「D1 构建后的 `content.json` 哈希 == 本地基线」这个判据不成立，比对时应忽略 `_generated` 段。
2. **D1 模式会重写受跟踪的 `data/content-dump.sql`**：`content-sync` 在 D1 模式下也会重新导出 SQL 快照。切回本地源再跑一次即可恢复；但**在 CI 里用 D1 构建会让工作区变脏**。如需规避，可在 D1 模式下跳过快照导出（尚未实现，属可选改进）。

## 9. 已知限制

以下问题**本次刻意保持现状**（不在本轮修复），后续维护者需要知道：

1. **`normalizeResult` 对缺 `success` 过于宽松**：只有 `result.success === false` 才判失败；
   缺字段或非 `false` 值都当成功。安全性依赖顶层 `success` 与 `errors[]` 检查，单条结果的
   异常结构不会单独报错。
2. **`D1ConfigError` 被复用于参数/用法错误**：配置缺失（缺环境变量）与参数非法（如 SQL 超限、
   绑定参数超 100、`selectAll` 自带 LIMIT）使用同一个错误类型，调用方无法只按类型区分
   「该去配环境变量」还是「SQL 写错了」。
3. **`materializeD1Snapshot` 吞掉 optional 表的所有异常**：`item_audio / audio_cleanup /
   audio_retired` 的读取失败一律 `continue`，可能掩盖网络/权限问题；好在它们不影响公开 JSON，
   但排查时不要忽略「某个私有表没读出来」的可能。
4. **`selectAll` 的 LIMIT/OFFSET 正则误伤字符串字面量**：只要 SQL 文本里出现 `limit`/`offset`
   单词（包括字符串字面量、列名、注释）就会被拒绝；反过来也无法用字符串字面量里带
   `LIMIT` 的 SQL。需要时请改用 `query()` 自己分页。
5. **`selectAll` 的 OFFSET 分页不是一致性快照**：两次查询之间发生写入时可能漏行/重复；
   构建期只读场景够用，强一致场景请用键集分页。
6. **`selectAllKeyset` 第一页必须提供 `firstPageSql`**：第一页没有上一页，若沿用带 cursor 条件的
   `sql`，占位符会比绑定参数多一个（旧实现会直接让 D1 报错）。现在缺 `firstPageSql` 会在本地
   快速失败，而不是发一个注定失败的请求；契约见 `d1-client.mjs` 的注释。
7. **`d1:push` 没有整体事务**：先删后插，中途失败会留下半空/半满的 D1；修正后重跑，没有自动回滚。
8. **`D1ApiError` 的手工构造不会打码**：打码依赖构造时传入 `secret`；调用方自己 new 时若不传，
   原始 `errors` 会保留（见第 4 节）。
9. **`.env` 不会自动加载**：仓库零依赖、没有 dotenv；所有变量必须由 shell / CI / Pages 面板注入。
10. **`--per-request` 上限 50 是保守值**：没有压测；`d1:push` 默认 20，不要为了快盲目调大。
11. **`d1:push --schema` 不补列**：远端已存在但缺列的表不会被修正，需要手工 `ALTER TABLE`。
12. **`sqlite_sequence` 尽力而为**：读或写失败不会中断主流程，只影响后续自增 id 起点。
13. **导出快照只含公开表**：管理工具私有目录不会随快照往返；重放还会级联清空本地 `item_audio`（见第 10 节）。

## 10. 恢复/回滚

### 10.1 先备份，再重放 `d1-export` 快照

`data/d1-export.sql` 的开头是：

```sql
PRAGMA foreign_keys = ON;
BEGIN;
DELETE FROM items; DELETE FROM stacks; DELETE FROM groups; DELETE FROM settings;
```

也就是说，把它重放到已有本地库会**先清空四张公开表**。更危险的是：`items` 上定义了
`ON DELETE CASCADE`，删除 `items` 会连带删除 `item_audio` 里对应的私有目录行
（D1 快照里没有这些数据，无法恢复）。

重放步骤：

1. **先备份**：停掉正在使用 `data/content.db` 的构建/管理工具，复制 `data/content.db`
   到安全位置（例如带日期的文件名）。`data/backups/` 目录被 gitignore，不会被提交。
2. 校验要重放的文件是刚从 D1 导出的那份，避免用旧的/手工编辑过的快照。
3. 重放：`sqlite3 data/content.db < data/d1-export.sql`。
4. 自检：`pnpm content:stats`、`pnpm content:check`、`pnpm content:sync`，
   确认行数、分组、音频路径都正常。
5. 如果结果不对：用第 1 步的备份覆盖 `data/content.db`，再重新跑 `pnpm content:sync`。

### 10.2 D1 侧回滚

- `d1:push` 是「清空 + 插入」，**没有自动回滚**。如果推错了，正确做法是：恢复本地正确内容库，
  再执行一次 `pnpm d1:push --yes`。
- `d1:export` 快照是**只读审计/备份**，本仓库没有「快照 → D1」的命令；不要手工把快照文件
  丢给 D1 执行，除非你清楚它在远端也会先删表。
- 推送前先跑 dry-run 看计划；如果本地表全空，默认拒绝执行（防误清空）。
- `sqlite_sequence` 写失败只影响后续自增起点；用 `--no-sequence` 可完全跳过。

### 10.3 把内容源切回本地

如果 D1 构建把 `src/data/content.json` / `data/content-dump.sql` 改成了云端版本，而你想恢复本地版本：

```bash
# 不设或清空 CONTENT_SOURCE，再跑一次
pnpm content:sync
```

如果本地库本身已经受损，先按 10.1 的备份恢复，再 sync。

## 11. 排错速查

| 现象 | 可能原因 / 处理 |
|---|---|
| `D1ConfigError`，信息列出 `CLOUDFLARE_ACCOUNT_ID` 等 | 变量没设、设在了别的 shell、或 `.env` 不会自动加载。在**同一个** shell 里 export 后再跑 |
| HTTP 401 / 403 | Token 权限不足（读取要 D1 Read、推送要 D1 Edit）、账号 ID 或数据库 UUID 不匹配、Token 已撤销 |
| `查询 D1 失败：请求超时（超过 30000 ms）` | 网络/代理问题，或 D1 正忙（导出期间 D1 不可用）；可短时调整 `D1_TIMEOUT_MS`，但平台还有 30 秒硬限制 |
| `绑定参数 N 个，超过 D1 上限 100 个` | 自定义 SQL 参数过多；按第 6 节拆批 |
| `单条 SQL 有 N 字节，超过 D1 上限 100000 字节` | 内容行太长或批量太大；`d1-push` 会自动拆，自定义 SQL 需要自己拆 |
| `selectAll() 的 SQL 不能自带 LIMIT/OFFSET` | SQL 里出现了 `limit`/`offset` 单词；去掉后由方法追加分页 |
| `selectAllKeyset() 第一页必须提供 firstPageSql` | 按第 9 节第 6 条补 `firstPageSql`，或从 `lastKey` 续读 |
| `D1 导出超时：轮询 N 次仍未完成` | 导出任务未完成；检查网络/D1 状态。`exportSql()` 目前没有脚本调用，先把 `d1:export` 当成主路径 |
| 构建后 `content.json` 与本地不一致 | 当前 shell 里 `CONTENT_SOURCE=d1` 仍在生效；清掉后重新 `pnpm content:sync` |
| 推送中途失败，D1 只剩一部分数据 | 正常现象（无事务）；修好原因后重新 `pnpm d1:push --yes`，不要手工补数据 |
